# Board installation and remote controllers

Next-version tracker: [#34](https://github.com/SCarlsen7757/BobFX/issues/34), with configuration #35, WLED #36, layout #37, scenes #38, BUSY Bar #39 and hardware acceptance #40. These changes must be built/published before deploying them; the existing v0.7.0 image does not contain them.

## Devices and layout

1. Configure each WLED controller's actual LED outputs and enable realtime UDP reception. BobFX uses DNRGB packets, split into at most 489 pixels per packet, to support more than 490 pixels without oversized datagrams.
2. Open **WLED devices**, scan, and select the devices BobFX should control. **Locate** pulses only the chosen controller for five seconds, without selecting it implicitly. It returns to its native effect after the one-second realtime lease expires. Locate/settings are unavailable during games; stop manual output first.
3. If discovery is blocked, enter the device's private IPv4 address and HTTP port. BobFX checks `/json/info` before registering it. Device identity is its normalized MAC; rediscovery refreshes its address/count/port and persists valid metadata.
4. Open **Board layout** and use **Add board** to create named slots in one left-to-right row. Assign a registered, selected WLED controller using each card's dropdown, now or later. A controller can belong to only one board. The arrow buttons change board order; click a square to rename or rotate it. There is no fixed number of boards.
5. Each board has two equal strips, both starting at the same corner and running in opposite directions, with two edges per strip. Assignment generates a mapping from the reported LED total: before rotation, strip 1 follows top/right from top-left; strip 2 follows left/bottom from top-left. This assumes consecutive WLED output ranges. If the total does not divide by four, the largest multiple of four is mapped, the LEDs left over at the end stay dark, and the page says so; adjust the edge ranges if the strips are wired differently. **Advanced settings** exposes **Swap strips**, the two-strip template, and manual edge ranges for other output numbering/counts. Existing saved mappings are preserved. On each board tile, every strip's LEDs have their own color, a ring marks the first LED of each strip, and the tile counts any LEDs left unmapped; hover over a dot for its strip and LED number. Strips are worked out from the edge ranges: edges belong to the same strip when their LED numbers carry on around a corner. Each edge's zero-based range must fit the controller's count and cannot overlap another edge.
6. Use **Calibrate boards** to check the current draft without saving it. Stand on the near side shown on screen. One assigned board lights at a time: top blue, right green, near/bottom amber, left pink; a white marker travels clockwise. Other assigned boards are dark. Move the board left/right in the row and rotate in 90-degree steps until it matches the screen, then continue to the next assigned board. Unassigned slots are skipped. **Finish and save** saves the adjustments; **Cancel calibration** restores the draft from before calibration, including any earlier unsaved setup.
7. **Save layout** also saves incomplete layouts. Settings survive restart; running games do not. Games use assigned boards in their relative row order, without gaps for unassigned slots. Offline assigned boards retain their positions. Controllers without an assigned board receive no game frames, and a game without any assigned board runs without WLED output. Manual effects continue to use all selected devices. Unmapped LEDs on mapped boards are black. Idle sync remains under **Advanced settings**; the look and timing of the game lights are set on the **Light show** page.

Calibration reserves the lights and blocks games, manual effects, Locate, and other configuration writes. The browser renews its session every five seconds while visible and connected; the server expires it after fifteen seconds without renewal. Navigating away stops calibration, and closing/disconnecting the browser releases output through expiry if its stop request cannot arrive. WLED's one-second realtime lease then expires and native idle playback resumes. Reconnecting preserves the unsaved page draft; start calibration again or save it. Device errors appear on the affected board without stopping other boards.

After changing WLED's hardware count, scan again before remapping. If a device shrinks below an existing edge range, BobFX reports the mismatch and suppresses that board's frames rather than sending an invalid mapping. Other devices continue.

## Idle and game scenes

Enable idle sync, choose a master, select followers and use group 1–8. All members must use the same native WLED UDP port; change it in WLED first if necessary. BobFX persists the native sync group/brightness/color/effect/palette settings and configures master sending and follower receiving. Configure the master's idle playlist through WLED. After realtime game/manual output ends, BobFX releases realtime mode and mirrors the master's current brightness/color/effect parameters to followers without copying LED bounds or restarting the master's playlist. Subsequent native changes use WLED's notifier. Disabling the setup removes BobFX's previous native sync roles on reachable devices.

Every game starts with a fixed three-second pre-countdown; it cannot be changed or skipped. The boards follow the BUSY Bar's beats in the chosen color theme. Preparation spends 60% of it on a scanner that sweeps the row and returns once a second, 20% on pulses along the player top/bottom edges, then 20% on a chase around every edge. All boards pop white on each count, harder as GO approaches. GO appears when the game timer starts: for 0.75 seconds a burst in the theme's accent color races from the center of the row to both ends behind a white front, then blends into play over the next 0.75 seconds.

While the game is playing, the theme's gradient drifts slowly along the row under a slow breathing wave. Nothing flashes, and the level is capped well below the big moments (35% of full level at Calm, 55% at Lively). Drift and breathing have minimum rates, so the lights are never still at any setting: a frozen board means BobFX has stopped sending. The timing does not depend on remaining game time.

Ending uses three weakening flares over two seconds, each a ring expanding from the center of the row. Then, for three seconds by default, a comet with a fading tail runs the boards while the afterglow sinks to black. The comet starts at the configured laps per second and coasts down to a quarter of that. Neighboring perimeter loops alternate direction to form a figure-eight movement; interior boards continue along their edge to the next handoff. The path wraps to the first board after the final loop. Natural completion and manual Stop during play use this ending; Stop during preparation returns directly to idle. Sound delivery remains per enabled browser.

### Light show page

Open **Light show** to choose a color theme (Neon sunset, Aurora, Ember, or Custom with three gradient colors and an accent) and brightness (20–100%). For the playing phase, choose an intensity (Calm, Balanced, Lively) and a drift speed (25–200%). Countdown, GO and game over keep their timing so they stay in step with the BUSY Bar; the bar itself always uses its neon sunset art. Flare and comet duration, comet laps per second and, under **Advanced settings**, the frame rate are also set here.

Theme colors are converted for LEDs (scaled to full level, then gamma 2.2) on the assumption that WLED leaves realtime data uncorrected. That conversion, the brightness and the play levels need a check on the real boards.

**Test on the boards** plays Countdown + GO (6 seconds), Playing (30 seconds) or Game over (flare plus comet time) on the assigned boards with the settings on the page, saved or not. A test reserves the lights like calibration does: games, manual effects, Locate, calibration and configuration writes return 409 until it ends. It ends by itself, another test replaces it, and **Stop test**, saving, or leaving the page ends it early. Tests need at least one assigned board and are unavailable while a game or other output owns the lights.

WLED native sync does not automatically relay incoming realtime pixels. BobFX renders a single timeline and sends each board its own frame. UDP unicast is best effort; these protocols do not guarantee physically simultaneous display or acknowledge receipt. Firmware/router behavior and visual smoothness require hardware checks.

## BUSY Bar

Enable local Wi-Fi HTTP API access on the BUSY Bar and set its local device password. Open **Remote controllers** in BobFX, add the device's private address and HTTP port, and enter that password in **Device API password**. Use **Test connection** to verify it without enabling display control, then **Save controllers**. No cloud API token, manually created password file, or Docker overlay is needed.

This also works when running BobFX directly with `dotnet run --project BobFx.Core --launch-profile http`. Browse to the normal local HTTP address and configure the controller through the same page. Native execution saves application data beside the executable unless `Settings__DataPath` is set. In Docker, the existing `/app/data` volume handles persistence automatically.

The password field is write-only: saved passwords are never filled back into the page or included in installation-settings exports. Leave it blank to keep the current password; enter a new password to replace it. Enabled integrations reconnect when credentials change. Passwords are protected using ASP.NET Data Protection in the application's `credentials` directory, with its key ring stored alongside them. On Linux these directories are restricted to the service user. Back up and protect the entire data directory: the key ring is required to decrypt saved passwords and is not protected from someone with access to the whole volume. Existing Docker secret deployments remain supported as a fallback; a password saved from the web page takes precedence.

Each controller has independent enable and remote-control switches; multiple bars are supported. Local HTTP testing is supported without HTTPS enforcement. As with other BobFX controls, use the trusted LAN: HTTP does not encrypt the password in transit.

BUSY Bar screens use the Game page's neon sunset look on the 72x16 front display: an ink-to-purple sky with stars, a sliced yellow-to-pink sun, a pink horizon, a magenta grid floor running toward the viewer and cyan-tipped wireframe ridges. Between games an eight-second loop plays: the sun rises, a bold BOB FX logo in the sun's colors wipes in behind a mint edge, a glint crosses it, the logo dissolves and the sun sets. During play the logo stays up over a faster grid with mint speed streaks. Preparation dims the scene and counts down in bold, centred seconds in the sun's colors, thirteen rows tall: each number pops in white-hot and oversized, settles, and fades just before the next. Its three stages show on the border: a pink-to-yellow scanner, pulsing player edges, then a chase round all four edges. GO! is a short mint burst. When the game ends GAME OVER slams in, oversized and white-hot, in dusk pink and violet, as the sun flares three times in step with the boards' flashes; each flare lights the sky, sends a ring of sun colors outward and pulses the lettering a little more weakly. Then the sun sets and the lettering falls apart, its pixels dropping away and fading into the dusk the idle loop rises from. The boards' closing dot is not shown on the bar. The seconds are part of the animation file, not text drawn through the API. Remaining game time is not shown on the bar.

The bar plays native animation files. BobFX generates and automatically uploads five content-named `.anim` assets (about 400 KB in total) on the first observed APPS mode of each connection session; no manual files are needed. The container format follows the API version the bar reports: firmware **1.3+ (API 27.14 and later)** loads only `bicycle1`, which BobFX writes with delta frames; firmware **1.2.x (API 27.5)** loads only `bicycle0`, written as whole frames with the two scenic loops at half rate to stay small. The bar accepts a file it cannot load and shows an error icon instead, so any other API version pauses output and is probed again every thirty seconds. Each BUSY Bar plays the files locally at 20 FPS, GO! at about 30 FPS. Every draw command is a single `animation` element naming one of those files; BobFX never sends pixels, shapes or text. It sends one command when the screen changes and, for looping screens only, a once-per-second lease refresh. The three-second preparation is one play-once clip, at 20 FPS so its 50 ms frames keep time, so the bar counts 3, 2, 1 by itself from a single command. On firmware 1.3+ the clip has a named section per second (`from2` starts two seconds in), so a command sent late or repeated after a failure joins at the right number instead of restarting. A command naming a different file switches to it immediately; a refresh naming the same looping file uses `await_previous_end`, which keeps the current cycle running. Looping elements expire after fifteen seconds without a refresh, giving the once-per-second heartbeat headroom for Wi-Fi delays. Screen changes replace the existing scene and numeric text together without clearing the canvas first; this avoids exposing the clock between phases. Transient display failures retry after 250 ms, backing off to two seconds, and reuse uploaded assets. Missing/invalid-asset responses trigger asset repair. The countdown, GO! and the ending (as long as the boards' flash and dot together) are play-once clips with a lease of their length plus one second; a heartbeat never queues them again. All uploads and commands pause outside observed APPS mode or when the selector stream disconnects. Upload failures are retried, including re-uploading the assets in case the device rebooted. Formats and playback behavior were checked against the official definitions for [1.2.3](https://github.com/busy-app/busybar-firmware/blob/1.2.3/lib/anim_file/anim_file_format.h) and [1.3.1](https://github.com/busy-app/busybar-firmware/blob/1.3.1/lib/anim_file/anim_file_format.h), the [1.3.1 loader](https://github.com/busy-app/busybar-firmware/blob/1.3.1/lib/anim_file/components/anim_file_load.c) and the official [converter](https://github.com/busy-app/busybar-firmware/blob/1.3.1/scripts/seq2anim.py).

Hardware acceptance remains required: confirm the controller status shows the bar's API version with output enabled, that the initial upload succeeds and no load-error icon appears, let the idle loop run through several lease refreshes without stuttering or restarting, check that the countdown reaches 1 as GO! appears and that its scanner / player edges / all edges stages match the boards, leave APPS and return mid-countdown to confirm it rejoins at the right number, then check that the three ending flares match the boards' flashes and that GAME OVER has fallen away before the idle sunrise begins. Test APPS exit/re-entry, Wi-Fi loss/recovery and device reboot. `GET /api/screen?display=0` on the bar returns a bitmap of the front display for comparison. Timing follows the game coordinator, but phase commands and numeric text updates can still arrive late over Wi-Fi; native playback removes Wi-Fi timing from the individual animation frames.

To judge the art without the bar, run the backend tests with `BOBFX_BUSYBAR_PREVIEW` set to a directory. It receives a contact sheet per screen and `preview.html`, which plays every screen as an LED matrix at its stored frame rate. The bar never displays time of day. The rear monochrome screen is left to the device.

The adapter probes `/api/version` and enables the reviewed input schema, unchanged between API 27.5 and 27.15, at `/api/status/ws`. BobFX monitors the selector even when remote game buttons are disabled. Display writes and START / wheel-press game commands are allowed only after APPS mode is observed. The controller page shows the detected selector position. Other positions pause outgoing traffic; existing elements finish or expire as described above, and an already in-flight request may finish. The status connection remains open to detect APPS again.

Firmware reports selector movement events but does not provide a reliable initial-position query. On first connection or reconnection, move the selector away from APPS and back. BobFX waits with output paused while the position is unknown, when the stream is unavailable, or when the selector protocol is unsupported. Re-entering APPS resumes the current game phase without restarting the game.

In APPS mode, a physical START press starts a game when idle and pressing the scroll wheel (the bar's OK button) stops it when remote controls are enabled. BACK is left alone, because in APPS it closes the screen and returns to the bar's app list. Releases, BACK and turning the wheel are ignored. Duplicate presses are debounced; commands use the same coordinator as browser controls. Failures retry; one controller's failure does not stop another. Disabling/removing a controller cancels its connections. Test connection only probes the API version and works regardless of selector position.

Installed firmware and buttons cannot be verified without the actual bar. Protocol references: [official local HTTP API](https://docs.busy.app/bar/dev/http-api), [official state/input stream guide](https://busy-app.github.io/busylib-py/guides/device-state/), [official protobuf definitions](https://github.com/busy-app/busylib-py/tree/main/src/busylib/state_stream_proto). The reviewed display references were API 27.5.0 / firmware 1.2.3 and API 27.14.0 / firmware 1.3.1. WLED references: [JSON API](https://kno.wled.ge/interfaces/json-api/), [native sync](https://kno.wled.ge/interfaces/udp-notifier/), [pixel protocols](https://kno.wled.ge/interfaces/udp-realtime/).

## Storage, backup and API

Production/development Compose mounts a named `bobfx-data` volume at `/app/data`. The image creates the mount point owned by UID 1654. The rest of the production container stays read-only. For a host bind mount instead, create the host directory and give UID 1654 ownership before launching. Do not delete the volume during routine updates.

`settings.json` uses schema version 1. Saves write and flush a temporary file then atomically replace the previous file; rejected settings leave the saved file unchanged. Corrupt/unsupported files fail startup clearly, so restore a compatible backup rather than silently losing configuration. Snapshot copies prevent callers from changing live settings without a save.

Back up configuration through `GET /api/installation` or copy `/app/data/settings.json` out of the container. Restore through `PUT /api/installation` while output is idle, which validates before saving. Configuration exports exclude passwords. To preserve saved credentials too, back up the entire data directory including `credentials` and its `keys` subdirectory; otherwise re-enter passwords through the web page after restoring. Back up before upgrades; rollback requires a settings backup supported by the older application.

Backend operations, subject to existing host/CIDR/origin restrictions:

| Operation | Endpoint |
| --- | --- |
| Read/save complete settings | `GET` / `PUT /api/installation` |
| Save board/layout settings without overwriting controllers | `PUT /api/installation/layout` |
| Save light show look and animation timing | `PUT /api/installation/light-show` with `{ lightShow, animation }` |
| List built-in color themes | `GET /api/installation/light-show/themes` |
| Play/stop a light show test on the boards | `POST` / `DELETE /api/installation/light-show/test` |
| Save controllers and write-only password replacements | `PUT /api/installation/controllers` |
| Test an unsaved controller draft | `POST /api/installation/controllers/test` |
| Check/register a manual device | `POST /api/installation/devices/manual` with `{ "address": "192.168.1.20", "port": 80 }` |
| Locate a registered device | `POST /api/installation/devices/{mac}/locate` |
| Apply saved native idle sync | `POST /api/installation/idle-sync/apply` |
| Output/controller diagnostics | `GET /api/installation/status`, `GET /api/installation/controllers/status` |
| Save/replace a controller password | `PUT /api/installation/controllers/{id}/password` with `{ "password": "your-device-password" }` |
| Check whether a password is saved | `GET /api/installation/controllers/{id}/password` returns only `hasPassword` |

Settings contain `version`, `devices`, ordered `boards`, `idleSync`, `animation`, `lightShow` and `controllers`. `lightShow` holds `theme`, `custom` colors, `brightness`, `speed` and `intensity`; files saved before it existed load with its defaults. GET returns the complete shape for editing/import/export. Each board's `edges` array is top/right/bottom/left before rotation. Unassigned slots use `deviceMac: null` and may have an empty `edges` array. Version remains 1, and existing assigned layouts load unchanged. Device entries include MAC, name, address, HTTP port, reported LED count/UDP port and selected flag. JSON keys use camel case. Save conflicts return 409; invalid settings return 400; unreachable manual devices return 502. Saving via the API and applying native idle configuration are separate operations.

`POST /api/installation/calibration` starts a preview with `{ boards, activeBoardId }` and returns `{ sessionId, activeBoardId, expiresUtc }`. `PUT /api/installation/calibration/{sessionId}` updates the same draft shape and renews the fifteen-second lease; assigned board/controller membership cannot change during a session. `DELETE` on that path stops it without saving. Only the session ID returned at start can update/stop an active session. Installation snapshots and SignalR include a nullable `calibration` object with the session ID, active board ID, and expiry time. Invalid drafts return 400; ownership conflicts, expired updates, and mismatched sessions return 409. Stop is idempotent once calibration has ended.

`POST /api/installation/light-show/test` starts or replaces a test with `{ segment, lightShow, animation }`, where `segment` is `countdown`, `playing` or `gameOver`, and returns `{ segment, endsUtc }`. `DELETE` on that path stops it and is idempotent. Installation snapshots and SignalR include a nullable `lightShowTest` object. Invalid drafts and a layout without an assigned board return 400; ownership conflicts return 409.

## Deployment acceptance

Use ARM64 Raspberry Pi OS and Docker Engine on the travel router LAN. Keep the Pi wired when possible; disable Wi-Fi client isolation. Build/CI and API tests do not establish actual LED receipt, idle playlist recovery, or Pi frame-rate capacity.

Record in [#40](https://github.com/SCarlsen7757/BobFX/issues/40): Pi/router models and firmware, image digest, volume recreation/backup restoration, changed IP rediscovery, each board's Locate, scanner/player edges/chase with the count pops, GO burst, calm but never still play at each intensity, three flares and the ending comet, theme colors and brightness as they look on the LEDs, each Light show test, native idle recovery, BUSY Bar input/display/secret authentication, device disconnect/recovery, CPU/memory and achieved frame cadence. The integrated Vue app has passed real WLED registration, Locate, mapped game start/stop and realtime-release checks against a 17-LED WLED 16.0.1 device. BUSY Bar API 27.5.0 authenticated through the browser using the operator-provided Proton Pass credential, which stayed out of traces and configuration exports. No APPS selector transition was observed during that hardware test, so physical START/BACK and visual BUSY Bar playback acceptance remain open. The hardened container persistence/recreation smoke test passes locally.
